## Critical gaps (ranked by risk)

1. **RLS cross-user test suite (`tests/integration/rls.test.ts`) — missing, and the spec marks it CI-blocking/merge-blocking.** This is the only layer the spec explicitly says must gate every PR touching `docs/specs/supabase-schema.sql`, including the Storage-bucket cross-user sub-suite (signed URL / download / remove on another user's file path). Nothing enforces that RLS policies actually behave as documented — the security plan's "Already correct" section asserts RLS is sound by code review, but that claim has no automated backstop. Highest risk of the missing layers: a regression here is a silent cross-tenant data leak, not a crashed test.
2. **Chat hallucination regression test (`tests/integration/chat-hallucination.test.ts`) — missing, and the spec ties it to a named target metric (≤5% hallucination rate across a 50 Q&A eval set) and a specific required output string ("I cannot find this in the document.").** This is the correctness backstop for the just-built Conversation Memory Layer and its classify→retrieve→prompt pipeline — exactly the kind of feature where a prompt regression is easy to introduce silently (the security plan's own text flags "the same kind of regression cycle the chat prompts went through in this session's earlier work" as a known risk). Currently nothing would catch a prompt change that starts fabricating answers instead of admitting absence.
3. **Integration coverage gap on 5 of 8 route handlers** (`process`, `contracts/[id]` DELETE, `account` DELETE, `auth/login`, `auth/logout`) — no happy-path or auth-failure test for any of them. `process` in particular is the extraction pipeline's entry point and has zero test coverage of its own (only exercised transitively via unit tests on its dependencies).
4. **Offline AI eval harness absent** — no automated check on extraction F1/precision/recall or page-attribution accuracy, both of which the spec ties to hard release gates (F1 ≥88%/85%, page accuracy ≥92% at the `public` launch profile). Currently nothing would block a regression in extraction quality from shipping.
5. **No E2E, accessibility, or load test infrastructure** — expected at this stage (Stage 5 has just started and the task scope explicitly excludes building these out), but flagging that none of the 4 PRD user flows the spec requires E2E coverage for (signup→dashboard, returning-user→dashboard, core review, chat) currently have any automated safety net at all — unit/integration tests mock every external dependency, so a live wiring break (e.g. a bad `.env`, a broken Supabase Storage bucket, a changed OpenAI param) would only surface manually.
6. **`lib/**` coverage is unmeasured**, not just below target — `jest.config.js` has no `collectCoverage`/`collectCoverageFrom`, so the spec's ≥80% line-coverage target can't currently be checked at all without a config change.

## Spot-check findings

- **Chat route history-before-insert ordering: correct.** `app/api/contracts/[contractId]/chat/route.ts` calls `loadMessages(session.id, turnLimit)` (line 62) before the new user message is inserted via `supabaseServer.from('chat_messages').insert(...)` (lines 69–79) — the bug described as previously fixed is still fixed. The code has an inline comment explaining why (avoiding the new message polluting its own history window).
- **Ownership checks on mutating routes: correct, no gaps found.** Every mutating route that operates on an existing resource-by-ID calls `loadContractOwnedBy()` and checks the null case before acting: `app/api/contracts/[contractId]/process/route.ts` (line 15-16), `app/api/contracts/[contractId]/route.ts` DELETE (line 11-12), `app/api/contracts/[contractId]/chat/route.ts` (line 25-33, plus the additional explicit `verifyContractOwnership`/`verifySessionOwnership` defense-in-depth checks from the security pass). `POST /api/contracts` (create) and `DELETE /api/account` (acts on the caller's own `userId`, no separate resource ID) correctly have no ownership check to make. Inline key-term correction (`PATCH`-equivalent) is a direct Supabase-client call per `docs/specs/08-inline-correction.md`, relying on the `key_terms_update_own` RLS policy by design — not a Route Handler gap.
- **`VALIDATION_ERROR` error code — spec deviation worth a second look.** `docs/specs/00-overview-and-conventions.md` states explicitly: *"There is no generic `VALIDATION_ERROR` fallback code in this project... `ApiErrorCode` intentionally has no catch-all validation member."* The security pass added `'VALIDATION_ERROR'` to `types/domain.ts`'s `ApiErrorCode` union and `app/api/auth/login/route.ts` uses it for the login-payload zod failure, rather than a domain-specific code (e.g. `INVALID_LOGIN_INPUT`). Low severity (auth/login is a new route, not a spec'd one at the time `00-overview` was written, so the convention may just not have been revisited) but it's a direct contradiction of a documented cross-cutting rule and worth a conscious decision — either rename the code or amend spec 00.
- **`rate_limit_events` check-then-insert race** (already flagged as an outstanding item in `docs/security/security-plan.md`) — confirmed by reading `lib/security/rateLimiter.ts`: `checkRateLimit()` does a `SELECT count` then a separate `INSERT`, non-atomically. Re-flagging here only because it's now also a testing gap: there's no test (unit or load) that would ever catch a burst-over-limit regression, since the RLS/load layers that could exercise concurrent requests don't exist yet either.
- **No other correctness red flags observed** in the routes and security modules read for this pass (`app/api/**/route.ts`, `lib/security/*.ts`, `lib/api/withApiAuth.ts`, `lib/api/loadContractOwnedBy.ts`).
