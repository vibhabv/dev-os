# ContractIQ — Security Plan

Generated by `skills/security-foundation/SKILL.md`, run against the existing codebase (auth, chat, uploads, and the Conversation Memory Layer were already built — this was an audit-and-fix pass, not a pre-feature scaffold, which is why some choices below deliberately diverge from the skill's generic template in favor of what was already approved, tested, and spec'd).

## Issues found and fixed

| # | Issue | Severity | Fix |
|---|---|---|---|
| 1 | `rate_limit_events` reads/writes went through the caller's own authenticated Supabase client, subject to RLS, instead of the service-role client. The existing RLS policies were correctly scoped (no live bypass), but this left the control's integrity dependent on RLS policy correctness rather than being independent of it. | Medium | `lib/security/rateLimiter.ts` now reads and writes exclusively via `createSupabaseAdminClient()`. `rate_limit_events_select_own`/`_insert_own` RLS policies dropped entirely (`supabase/rls-policies.sql`, `docs/specs/supabase-schema-additions.sql`, `database.sql`) — a user hitting the Supabase REST API directly with their own JWT can no longer read or write this table at all. |
| 2 | `POST /api/contracts` (contract upload) had no rate limiting at all. | Medium | Added a new `upload` rate-limit action (20/day), wired via `withApiAuth(..., { rateLimitAction: 'upload' })`. |
| 3 | File upload validation was a single loose check (`file.type === 'application/pdf' \|\| filename.endsWith('.pdf')`, OR logic) with no explicit blocklist and no defined validation order — a renamed executable with a forged `Content-Type: application/pdf` header could pass the filename-only branch. | Medium | `lib/security/inputValidator.ts`'s `validateFileUpload()`: blocked-extension → allowed-extension → MIME type → size, in that order, all required (AND logic). Wired into `app/api/contracts/route.ts`. |
| 4 | No prompt injection defense on chat messages — user input went straight into the OpenAI call. | Medium | `lib/security/promptInjectionGuard.ts`'s `sanitizeForLLM()`, called before any DB write or OpenAI call in the chat route; returns `400 PROMPT_INJECTION_DETECTED` and never calls OpenAI on detection. |
| 5 | Login/logout ran entirely client-side (`components/auth/*`, `hooks/useAuth.ts`), with no server-side route to centralize session handling. | Low | Added `app/api/auth/login/route.ts` and `app/api/auth/logout/route.ts`. `useAuth.ts`'s `signOut()` now calls `POST /api/auth/logout` first (see "Deliberate deviations" below for why `SignInModal.tsx` was not also migrated). |
| 6 | No explicit, named ownership assertions on the chat surface — contract/session ownership was correct by construction (`loadContractOwnedBy` already filters; `chat_sessions.contract_id` is unique per contract) but not asserted as a standalone, defense-in-depth check. | Low | `lib/security/chatSecurity.ts`'s `verifyContractOwnership()`/`verifySessionOwnership()`, wired into the chat route as explicit checks alongside the existing query-level filtering. |
| 7 | `withApiAuth`'s `429 RATE_LIMITED` response had no `Retry-After` header. | Low | Added via `retryAfterSeconds()` (`lib/security/rateLimiter.ts`). |
| 8 | No single, named ceiling on how much chat history one call could ever request, independent of the Conversation Memory Layer's own per-classification limits. | Low (defense in depth) | `MAX_CHAT_HISTORY` env var + `lib/security/tokenLimiter.ts`, clamped into the chat route's `turnLimit` via `Math.min(...)`. |

No critical or high-severity issues were found — auth, RLS, and secret handling were already sound (see "Already correct" below).

## Already correct (verified, not changed)

- **RLS**: every table holding user data already has RLS enabled with owner-scoped policies (`docs/specs/supabase-schema.sql`); no table was found world-readable or missing RLS.
- **Storage**: the `contracts` bucket is private (`public: false`); no code path generates or returns a public or signed URL for uploaded files — the app only ever reads back the extracted `contract_text`, not the original file.
- **Secrets**: `OPENAI_API_KEY` and `SUPABASE_SERVICE_ROLE_KEY` are server-only (no `NEXT_PUBLIC_` prefix); `createSupabaseAdminClient()` usage is confined to server-only files (`lib/supabase/admin.ts`, `app/api/account/route.ts`, `app/auth/callback/route.ts`, `netlify/functions/*.ts`). A full-codebase grep found no secret ever passed to `console.log`/`console.error`/`console.warn`.
- **Contract/session ownership on read paths**: `loadContractOwnedBy()` already filters by `user_id`; confirmed no route returns another user's contract or chat data.
- **No `eval()`, no `dangerouslySetInnerHTML`** anywhere in the codebase.
- **Chat message length**: already capped at 2000 chars via Zod (`lib/validation/chatMessageSchema.ts`) — stricter than this skill's own 5000-char guidance, kept as-is.
- **File size / page count**: already capped at 10 MB / 20 pages (`lib/pdf/validate.ts`) — stricter than this skill's 200-page guidance, kept as-is.

## Deliberate deviations from the skill's generic template

These are documented choices, not omissions:

1. **Rate limits kept at existing values, not the skill's illustrative table.** `process` (20/hour) and `chat` (60/hour) are already documented in `docs/specs/04-key-term-extraction.md` / `docs/specs/09-contract-chat-and-realtime.md` and covered by existing tests. The skill's example numbers (chat: 30/minute, process: 5/hour) would be a large, undiscussed behavior change to approved, shipped limits — not adopted. Only the two genuinely-missing surfaces (`upload`, `auth`) got new limits.
2. **File upload allowlist is `.pdf` only, not `.pdf` + `.docx`.** `lib/pdf/extractText.ts` only implements PDF parsing (`pdf-parse`) — `docs/specs/03-pdf-upload-and-extraction.md` is PDF-only end to end. Allowing `.docx` uploads would accept files the rest of the pipeline can't process.
3. **No app-level rate limit on `POST /api/auth/login`.** `rate_limit_events.user_id` is `NOT NULL` with a FK to `auth.users` — it cannot key a limiter on a request that doesn't yet resolve to a known user. Keying by email would create an email-enumeration timing side-channel; keying by IP wasn't available from this handler's inputs without broader request-context plumbing. Login abuse is covered by Supabase Auth's own server-side rate limiting, which applies regardless of what this app builds on top of it. The `auth` action is defined in `lib/security/rateLimiter.ts` for future use if a dedicated IP-or-email-keyed table is added.
4. **`SignInModal.tsx` was not migrated to `POST /api/auth/login`.** The existing client-side `signInWithPassword()` flow (via `@supabase/ssr`'s browser client) already correctly sets cookies and correctly updates reactive auth state via `onAuthStateChange`. Migrating to the server route would require resyncing the browser client's local session state after a server-side sign-in, which risks silently breaking a currently-working, tested sign-in flow without the ability to verify the fix in a live browser during this session. The login route exists and is production-ready and available as a deliverable; wiring the UI to it is left as a follow-up with browser-based verification.
5. **`middleware.ts` route matcher and redirect target were not changed to literally match the skill's `/dashboard`, `/contracts`, `/chat`, `/settings`, `/profile`, `/login` list.** This app doesn't have standalone `/chat`, `/settings`, `/profile`, or `/login` routes — chat is a panel inside `/contracts/[contractId]`, settings lives at `/account` (already in the matcher), and sign-in is a modal on the marketing page, not a route. The existing matcher (`/dashboard/:path*`, `/contracts/:path*`, `/account`) already covers every actual protected page; redirecting unauthenticated users to `/` with a `?redirect=` param (which `SignInModal.tsx` reads to return them post-login) is the equivalent of the skill's `/login` redirect for this app's actual UX.
6. **Prompt injection embedded in uploaded contract text (extraction path) was not mitigated in this pass.** `sanitizeForLLM()` is applied to chat messages, which are literally user-typed input — an appropriate scope for pattern-based blocking. Contract text is different: it's attacker-controllable but must still be sent to the model verbatim for extraction to work at all, so it can't be pattern-blocked the same way without breaking the feature. `runExtraction()`'s output is already Zod-validated (`extractionResultSchema`, rejecting malformed structure as `INVALID_MODEL_OUTPUT`), which catches structurally-invalid manipulation attempts, but a malicious contract could still get the model to extract a structurally-valid but semantically-wrong value (e.g. a fabricated termination fee). A real fix here means prompt-hardening the extraction system prompts, which risks the same kind of regression cycle the chat prompts went through in this session's earlier work, and deserves dedicated testing rather than a rushed change bundled into this audit. **Listed as an outstanding item below.**

## Outstanding items (not fixed in this pass)

- **Extraction-path prompt injection** (deviation 6 above) — needs a dedicated pass with its own eval/regression testing, not bundled here.
- **`SignInModal.tsx` → `/api/auth/login` migration** (deviation 4 above) — needs live-browser verification of the client-side session resync.
- **CSRF**: no route in this codebase (not just the ones touched here) uses a CSRF token; protection currently relies on Supabase's default `SameSite=Lax` cookie behavior. Worth a dedicated review if the app ever needs to support cross-origin embedding.
- **Supabase Dashboard settings** (not code-controllable) — verify manually: email verification is required, password reset flow is enabled, session/refresh-token rotation is on.
- **`rate_limit_events` check-then-insert race**: `checkRateLimit()` isn't atomic — two near-simultaneous requests can both pass the count check before either inserts, allowing a burst of `+1` over the limit. Pre-existing behavior, not introduced or fixed in this pass; would need a DB-level atomic increment (e.g. a stored procedure) to close.
