**New gaps found in this round's fresh audit (not previously raised):**

1. **`beta_access` cohort-cap atomicity — spec directly contradicts engineering doc's factual claim.** Engineering doc Section 7 (`beta_access` table description) states the service-role insert "atomically counts existing rows and inserts only if the count is below 50, **preventing a race condition** from over-admitting the cohort" — asserted as a property of the actual mechanism, not an aspiration. `docs/specs/01-auth-and-session.md`'s actual `app/auth/callback/route.ts` code implements a plain two-step `count()` then `insert()` and the spec's own prose admits "the count-then-insert is not atomic against concurrent callbacks," proposing the atomic `SECURITY DEFINER` RPC only as an optional, undocumented "follow-up." This is a direct contradiction of the eng-doc's stated guarantee, not just a missing detail — needs either implementing the atomic RPC to match the eng-doc's claim, or an explicit reconciliation note (matching this project's own convention for resolving cross-doc tensions, e.g. the FR-05 fix in round 1).
2. **`withRetry()` used but never defined anywhere.** Used identically to `withTimeout()` in `04-key-term-extraction.md` and `09-contract-chat-and-realtime.md` (and referenced in `00-overview-and-conventions.md` line ~129 and `13-rate-limiting-and-cost-control.md`) to implement the PRD/eng-doc's explicit "3 retries with exponential backoff (1s/2s/4s) for transient errors (5xx, timeout, 429)" requirement (engineering doc Section 6/8). Unlike `withTimeout` (which got a full implementation + file path `lib/openai/withTimeout.ts` in 00 specifically because round 1 flagged the analogous gap), `withRetry` has no declared file location, signature, or — critically — any statement of which error conditions are treated as retryable vs. immediately fatal. Without that, it's unverifiable whether a non-transient OpenAI 400 gets wastefully retried 3x (blowing the 20s-per-call / 30s-total budgets) or correctly fails fast.
3. **Page-attribution accuracy (≥92%) named as a CI-blocking release gate in the engineering doc but never wired into any actual gate implementation in the specs.** Engineering doc Section 8 ("Post-launch AI monitoring cadence," Every-deploy bullet) states explicitly: "a release cannot promote to production if F1 falls below 88% (NDA) / 85% (MSA) or **page-attribution accuracy falls below 92%**." `docs/specs/02-beta-access-and-launch-gates.md`'s `--gate=<stage>` threshold table (the actual CI-gate implementation) and `docs/specs/18-testing-and-eval-strategy.md`'s "CI pipeline gates" section both list only F1/latency/correction-rate/calibration-error/satisfaction as enforced columns — page-attribution accuracy is mentioned only as an eval *category name* ("page-number accuracy") with no numeric threshold or blocking behavior specified anywhere in `docs/specs/`.
4. **`VALIDATION_ERROR` is a declared-but-unreachable error code, and contradicts 00's own stated rule.** `00-overview-and-conventions.md` declares `VALIDATION_ERROR` in the `ApiErrorCode` union, the HTTP-status table, and states as a general rule (line 147): "All Route Handler JSON bodies are validated with zod schemas... On failure, return `400 VALIDATION_ERROR` with `fields` populated from `error.flatten().fieldErrors`." But grepping every route handler code sample across all 20 spec files, `VALIDATION_ERROR` is never actually returned anywhere — every documented zod/manual validation failure maps to a more specific code instead (`INVALID_CONTRACT_TYPE` in 03, `INVALID_MESSAGE` in 09, `CONFIRMATION_REQUIRED` in 12). This is the same "declared-but-unreachable error code" pattern round 1 caught for `INVALID_CONTRACT_TYPE` (issue #2), just for a different code, and it also directly contradicts 00's own general validation rule.

**Note for next round:** verify these 4 items are fixed via genuine code/definition changes, not just a reconciliation sentence — items 2 and 3 in particular need concrete artifacts (a `withRetry` definition with file path + retryable-error criteria; an actual numeric threshold wired into the gate table/CI logic for page-attribution accuracy), not just prose acknowledging the gap.

**New gaps found in this round's fresh audit (not previously raised):**

1. **`loadContractOwnedBy()` — used identically across 3 route-handler spec files (04-key-term-extraction.md, 09-contract-chat-and-realtime.md, 14-retention-and-deletion.md) to implement the security-critical "Ownership re-verification (defense in depth)" rule stated in 00-overview-and-conventions.md — but is never formally defined anywhere: no file path, no signature, no return-value/throw shape.** This matters more than an ordinary undefined helper because `CONTRACT_NOT_FOUND` (00's declared `ApiErrorCode`, mapped to HTTP 404 in 00's own status table) is *never once* constructed via an actual `jsonError(...)` call at any concrete code site in the entire spec set — it only ever appears in prose/comments ("// 404 if missing/not owned", "else `404 CONTRACT_NOT_FOUND`" as a precondition bullet). The only generic error-handling fallback shown anywhere (`mapUnhandledErrorToEnvelope`, inside `withApiAuth`'s `catch` block in 00) is explicitly documented as returning "a 500 envelope as last resort" — meaning it is unspecified/unclear how a not-found-or-not-owned contract lookup ever actually produces the documented `404 CONTRACT_NOT_FOUND` response instead of silently falling through to a generic `500`. This is the same "declared-but-unreachable error code" + "referenced-but-undefined pervasive helper" pattern that triggered NEEDS REVISION in rounds 1 (`INVALID_CONTRACT_TYPE`), 2 (`withRetry`, `VALIDATION_ERROR`), and 3 (`jsonError`) — just for a previously-overlooked identifier pair (`loadContractOwnedBy` / `CONTRACT_NOT_FOUND`). Needs: a formal definition (file path, e.g. `lib/api/loadContractOwnedBy.ts`, signature, and an explicit statement of how/where it triggers a `jsonError('CONTRACT_NOT_FOUND', ..., 404, false)` response — not a thrown generic error swallowed by `mapUnhandledErrorToEnvelope`).
2. **`POST /api/contracts/{contractId}/process` success response (docs/specs/04-key-term-extraction.md) omits the `id` field on each `key_terms` array element, contradicting the engineering doc's own explicit documented response schema** (engineering-doc.md lines 672–682, which shows `"id": "uuid"` per key term). The route handler code builds `rows` purely from `result.terms.map(...)` (no `id` property) and calls `.insert(rows)` without chaining `.select()`, so DB-generated UUIDs are never retrieved — the handler then returns `key_terms: rows`, literally the pre-insert array, as the response body. Low practical blast radius (docs/specs/07's `useKeyTerms.ts` hook refetches fresh from the DB via a separate query rather than consuming this response body), but it is a concrete, verifiable schema mismatch between this implementation spec and the engineering doc's own API contract for the same endpoint.

**Note for next round:** verify both items are fixed with concrete artifacts (a real `loadContractOwnedBy` definition showing the `CONTRACT_NOT_FOUND` 404 path explicitly, not just a renamed comment; and either `.select()` chained onto the `key_terms` insert with the DB-returned rows used in the response, or an explicit, reasoned deviation note if `id` is intentionally omitted). Also re-verify all rounds 1–3 fixes remain intact, since fixes in one file can regress others.
