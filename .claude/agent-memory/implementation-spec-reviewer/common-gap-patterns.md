Patterns worth specifically hunting for on every audit round of this kind of spec set (learned from [[contractiq-review-log]] round 1):

- **Cross-file code-contract mismatches on shared helpers.** When a spec file (e.g. 00-overview) declares a canonical function signature (like `withApiAuth(handler, opts?)`), grep every OTHER spec file's actual code sample that calls it and verify argument order/presence matches exactly. Prose claims ("wrapped in X with option Y") are not enough — check the literal code block, since prose and code sample within the *same* file can also drift apart (seen in docs/specs/04: prose said rate-limit option was applied, code sample omitted it).
  Why: these are easy for a spec author to get right in one file and wrong in a sibling file since each spec file is often drafted semi-independently.
  How to apply: for every cross-cutting utility (auth wrapper, error envelope, retry helper), collect all call sites across all spec files in one pass and diff them against the canonical declaration before declaring "runnable."

- **Declared-but-unreachable error codes.** When a shared error-code enum/status-mapping table (00-overview) lists a specific code (e.g. `INVALID_CONTRACT_TYPE`) for a named scenario, verify the actual route handler spec for that scenario emits exactly that code and not a generic fallback (e.g. `VALIDATION_ERROR`). Also check the engineering doc's own per-endpoint "Error responses" list — it's often the source of truth for which specific code an endpoint should return.

- **Documented-but-unimplemented error paths (e.g. TIMEOUT/504).** If an endpoint's error-response list in the eng-doc includes a status/code, confirm the spec's actual code sample has a code path that can produce it — not just a catch-all mapping everything to one generic error.

- **Absolute claims with silent exceptions.** Watch for "every X does Y" language in a foundational spec file (00-overview) that a later spec file (e.g. 16) contradicts by carving out an exception "per [that same foundational file]" — the foundational file needs the exception stated explicitly, not asserted elsewhere.

- **PRD-internal wording contradictions that were never explicitly reconciled.** This project's convention (visible in engineering-doc.md) is to explicitly call out and resolve PRD contradictions with a stated rationale (e.g. DPA scoping in Section 6, chat-history length in Section 8 vs Assumption 14). When a PRD contradiction exists (e.g. FR-05 "at least 5" vs Constraints "maximum 5") and neither the eng-doc nor the relevant spec file acknowledges/reconciles it the same way, that's a real gap to flag — even though the implementation's chosen interpretation may be reasonable.

- **Test-coverage scoping gaps.** When a testing spec says "RLS tests for every table," check whether Storage (`storage.objects`) RLS policies — which live in the same schema file but aren't a "table" in the enumerated sense — are explicitly included or silently excluded.

- **Referenced-but-undefined constants/helpers.** Grep for identifiers used in code samples (e.g. `CHAT_PROMPT_VERSION`, `sha256`, `withRetry`) and confirm each has a stated home file/definition somewhere in the spec set, especially when an analogous sibling identifier (e.g. `PROMPT_VERSION`) IS explicitly documented elsewhere — the asymmetry is usually a genuine oversight, not an intentional omission.
  Round 2 example: `withTimeout()` got a full implementation + file path in 00-overview specifically because round 1 flagged the gap for it, but the structurally-identical `withRetry()` (used the same way, in the same two routes, implementing the same "3x exponential backoff" reliability requirement) never got the same treatment — still just a bare function call with no definition, no file path, and no statement of which errors are retryable vs. fatal. **Fixing one instance of this pattern does not mean sibling instances are fixed too — always grep for ALL cross-cutting helpers, not just the ones previously flagged.**

- **Spec directly contradicts a source document's factual claim (distinct from a missing-detail gap).** Watch for cases where the engineering doc states a property of a mechanism as fact (e.g. "atomically counts... preventing a race condition") and the implementation spec then implements something that does NOT have that property, while explicitly admitting so in its own prose (e.g. "not atomic against concurrent callbacks... acceptable... documented follow-up, not blocking"). This is not a reconciled ambiguity (like the FR-05 wording-tension fix) — it's an unreconciled contradiction where the spec quietly ships a materially different guarantee than what the upstream doc asserts. Round 2 example: `beta_access` cohort-cap insert in docs/specs/01, contradicting engineering-doc.md Section 7's atomicity claim.

- **CI-blocking / gate-enforcement criteria named in prose but not wired into the actual gate table.** When a source doc states a specific numeric threshold is release-blocking (e.g. "a release cannot promote to production if ... page-attribution accuracy falls below 92%"), verify the spec's actual gate implementation (a `--gate=<stage>` threshold table, a CI pipeline gates list, etc.) includes that exact metric as an enforced column — not just as a category name in a prose list elsewhere. Round 2 example: page-attribution accuracy (92%) named as CI-blocking in engineering-doc.md Section 8, but the gate table in docs/specs/02 and the CI pipeline gates section in docs/specs/18 only enforce F1/latency/correction-rate/calibration/satisfaction — 92% page accuracy never appears as an actual threshold anywhere.

- **The single most-used cross-cutting helper is the one most likely to be skipped when auditing "referenced-but-undefined" helpers.** Round 3 example: `jsonError()` is called with a consistent 4-arg signature at 20+ call sites across nearly every route-handler spec file (00, 03, 04, 09, 12, 14) — far more pervasive than `withTimeout`/`withRetry`, which got full definitions specifically because round 1/2 flagged them — yet `jsonError` itself was never given a file path or signature anywhere in the spec set, and this survived two full review rounds unnoticed. Lesson: don't just grep for the helpers already flagged in memory; grep fresh for every capitalized/camelCase function identifier used across ≥3 files each round, and check whether *each one* has a declared home, not just the previously-burned ones. Also check whether an optional parameter documented in the shared contract (here: `ApiError.fields`, populated from zod's `error.flatten().fieldErrors` per 00's own "Request validation" section) is ever actually passed at a real call site — if every call site consistently omits it, that's a declared-but-unreachable field, same category as declared-but-unreachable error codes.

- **Eng-doc-internal self-contradictions within a single endpoint's own spec paragraph.** Not just PRD-vs-PRD or PRD-vs-eng-doc tensions — check whether a single section of the engineering doc contradicts itself between adjacent sentences/bullets (e.g. a "Validation" bullet asserting one status code for a scenario, and the very next "Error responses" bullet's enumerated list containing a different code for the same scenario, with no overlap). Round 3 example: engineering-doc.md Section 9's `POST /api/contracts/{contractId}/process` spec says "already-`completed` contracts return `409`" in its Validation bullet, but the Error-responses bullet immediately below lists only `400 ALREADY_PROCESSED` with no `409` anywhere — docs/specs/04 silently implements 400 without any reconciliation note, unlike this project's own established convention (e.g. 06's explicit FR-05 "at least 5 vs. maximum 5" reconciliation).

- **A literal PRD/eng-doc phrase can be technically wrong and the spec silently (correctly) deviates from it without saying so.** Round 3 example: PRD FR-14 and engineering-doc.md Sections 6/7 both state the Storage path pattern as `contracts/{user_id}/{contract_id}/{filename}.pdf` — but Supabase's `storage.foldername(name)[1]` RLS check only works correctly if the object's stored path (relative to the bucket) does NOT include a literal `contracts/` prefix (since the bucket itself is already named `contracts`); if taken literally, `foldername(name)[1]` would resolve to the string `"contracts"` instead of the user's UUID, breaking RLS entirely. The actual code in docs/specs/03/12/14 correctly omits the prefix, but supabase-schema.sql's own Storage-section comment still quotes the misleading PRD/eng-doc phrase verbatim, creating a documentation/implementation mismatch. When a path/format string appears in both the PRD/eng-doc AND in schema/code comments AND in actual executable logic, verify all three actually agree — don't assume a verbatim-copied comment is harmless just because the executable code happens to be correct. Fixed in round 3's revision.

- **A resource-loading helper paired 1:1 with a specific declared error code needs the SAME "referenced-but-undefined" scrutiny as request-handling helpers like jsonError/withRetry — don't stop hunting once the most obvious pervasive helper is fixed.** Round 4 example: `loadContractOwnedBy()` is called identically across 3 route-handler spec files (04, 09, 14) to implement 00's own "Ownership re-verification (defense in depth)" rule, and is the sole mechanism responsible for producing `404 CONTRACT_NOT_FOUND` (a declared `ApiErrorCode` with its own HTTP-status-table entry) — yet it has no file path, signature, or defined return/throw shape anywhere, and `CONTRACT_NOT_FOUND` is *never once* constructed via an actual `jsonError(...)` call at any concrete code site in the whole spec set (only ever appears in prose/comments like "// 404 if missing/not owned"). Worse, the only generic fallback shown (`mapUnhandledErrorToEnvelope` inside `withApiAuth`'s catch block) is explicitly documented as returning "a 500 envelope as last resort" — so it's actually unclear whether a not-found/not-owned lookup ever produces the documented 404 rather than silently degrading to a generic 500. Lesson: after a round fixes the most-obvious pervasive helper (jsonError in round 3), explicitly re-grep for OTHER helpers that are (a) called across ≥2 files with identical usage and (b) are the sole producer of a specific declared error code/status — these are just as likely to have been overlooked precisely because reviewer attention was focused elsewhere.

- **A route handler's success-response code sample can silently omit a field the engineering doc's own documented response schema for that exact endpoint includes.** Round 4 example: engineering-doc.md's `POST /api/contracts/{contractId}/process` response example (lines 672–682) shows `"id": "uuid"` on each `key_terms` array element, but docs/specs/04's actual route handler builds the `rows` array purely from `result.terms.map(...)` (no `id` property) and calls `.insert(rows)` without chaining `.select()`, so DB-generated UUIDs are never fetched back — the handler then returns `key_terms: rows`, literally the pre-insert local array, not DB-returned rows. Low blast radius here since the frontend (docs/specs/07) refetches key terms via a separate query rather than consuming this response body, but it's still a concrete, verifiable contract-schema mismatch. When auditing a route handler's response, diff its actual returned object shape field-by-field against the engineering doc's own JSON example for that same endpoint — not just check that a response is returned at all.
