## Patterns observed (useful for future audits of this planner)
- When the planner fixes a flagged issue, it tends to fix it narrowly and literally — it does not automatically re-scan sibling items in the same PRD list/table for completeness. E.g., Round 1 flagged "dependency tracking incomplete" citing 2 missing items; planner added exactly those 2 and left a 3rd, unflagged sibling bullet in the same PRD list untouched, and introduced a section-citation error while doing so.
- Similarly, when building a new mechanism to satisfy one part of a PRD table (e.g., Section 13 gate table for Launch Criteria "Go Criteria"/Honest columns), the planner does not necessarily carry over ALL columns/pillars from the source PRD table (missed Helpful/Harmless columns).
- Actionable takeaway for future rounds: whenever a fix references "PRD Section X, list/table Y," re-read that entire list/table in the PRD (not just the previously-quoted bullets) to check for uncovered siblings, and re-check any newly-built table against every column of its PRD source table, not just the ones the fix targeted.
- Round 3 reinforced this: the round-2 dependency-tracking fix (Section 6) was internally correct in isolation, but a *different* section (Section 13's Public Launch gate row) that references "the Section 6 dependency checklist" wasn't updated to cite the specific right bullet (GDPR DPA vs. general ToS/DPA review) — cross-references into a fixed section can still go stale even when the section being pointed at is itself now correct. Always trace every place in the doc that *cites* a just-fixed section, not just the section itself.
- Whole-table PRD items with concrete timed SLAs embedded in prose (e.g. Section 11 Reliability & Safety "Customer communication plan": P0 = email affected users within 1 hour + status page within 30 min; P1 = banner within 2 hours) are easy to miss entirely because they're phrasally similar to narrative/Responsible-AI answers elsewhere that don't need literal engineering implementation — but these ones do carry concrete, testable operational commitments and should be greped for explicitly (numbers, "within X hour/minute", named artifacts like "status page") each round.
- Round 4 reinforced and extended this pattern twice more: (a) an entire Responsible-AI *pillar* (Fairness) — not just a row — was silently dropped while its three sibling pillars (Accountability, Transparency, Reliability & Safety) were all thoroughly and explicitly implemented; when a PRD section has 4 named subsections, explicitly checklist all 4 by name every round, don't just spot-check the ones previously flagged. (b) When the planner adds a brand-new mechanism to fix a flagged gap (e.g. Round 3's incident-response fix), it reliably updates the section directly containing the fix and the folder structure, but does NOT reliably propagate the new feature area into the doc's own "enumerate every MVP feature" summary tables (Section 10 Feature Breakdown, Section 14 Specs-to-Implementation Mapping) — always check newly-added mechanisms against both of those tables specifically in the round immediately following their introduction.
- Round 5 found the sharpest instance yet of the "fixes only the literally-quoted sub-clause" pattern: the Round 4 Fairness fix targeted a PRD table *cell* containing two semicolon-separated clauses ("Monthly accuracy audit segmented by...jurisdiction...and industry; user feedback tagged with contract type helps surface systematic gaps") — the fix thoroughly handled clause 1 but completely dropped clause 2, even though Round 4's own finding text had quoted the full cell including clause 2. Actionable refinement: when a PRD table cell contains multiple semicolon- or comma-joined clauses, treat each clause as an independently-checkable sub-item in the checklist, not just the cell as a whole — a "fixed" cell can still be a partial fix at the clause level.
